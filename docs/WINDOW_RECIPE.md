# 0.7.0 매개변수형 두 짝 미닫이 창

## 전달 방식과 줄인 비용

일반 변경은 MCP 어댑터 → GUI 중개 앱 → SketchUp 확장으로 전달되고 각 전송 경계에서 JSON을 읽습니다. 이미 있는 `sketchup_run_batch`는 최대64단계를 **하나의 메시지**로 보내며, 플러그인 안에서 Ruby Hash를 순회합니다. 단계마다 새 파이프 메시지를 보내거나 JSON을 다시 파싱하는 구조가 아닙니다. 단, 뒤 단계가 앞 단계의 생성 ID를 동적으로 참조하는 표현식은 지원하지 않습니다.

이번 창 최적화에서는 면/선 약660개를 개별 조회하며 재질·평면·구조를 판단했습니다. 각 조회의 호출 왕복과 응답 처리, 대화 단계가 반복됐습니다. 형상 생성 batch 본문은 당시29–58ms였지만 이 수치는 전체 작업 시간이나 파싱 비용 측정이 아닙니다. JSON 파싱 자체의 비중은 측정하지 않았습니다. 확장은50ms UI 타이머에서 수신을 처리하므로 개별 요청의 순차 왕복에도 비용이 생깁니다.

새 `sketchup_create_sliding_window`는 치수·원점·구성·기존 재질 이름을 **한 요청**으로 받습니다. 플러그인 안의 순수 수치 계획기 → native 형상 생성 → 재질 지정 → 접합선 정리 → 외곽/솔리드 확인을 하나의 operation/Undo로 실행합니다. 모양을 알기 때문에 각 면/선 정보를 다시 MCP로 읽어올 필요가 없습니다. 한 요청은 전송 경계의 파싱을 없애는 것이 아니라 반복 요청을 줄입니다.

## 입력과 결과

공통 session_id/model_id/command_id/expected_context에 다음 필드를 더합니다.

| 필드 | 기본값·범위 |
| --- | --- |
| name, origin_mm | 필수. 모델 축 기준 외곽 왼쪽·앞·아래 원점 |
| width_mm / height_mm / depth_mm | 필수. 각각600–6000 / 400–3600 / 80–300mm |
| frame_width_mm / sash_width_mm | 40 / 35mm. 각각30–100 / 20–80 |
| glass_thickness_mm | 6mm. 범위3–12 |
| overlap_mm | 창짝 폭+5mm(기본40). 범위20–160, 창짝 폭과의 추가 적합성 검사 |
| open_sash / open_fraction | none / 0. left 또는 right, 이동 가능 거리의0–1 |
| materials | 필수. frame/glass/seal/hardware에 기존 모델 재질의 정확한 이름 |
| replace_entity_id | 선택. 현재 편집 위치의 직접 그룹/컴포넌트 하나를 성공 후 교체 |
| dry_run | 공통 선택. 형상·Undo 없이 계획/재질/대상 검증, 명령 ID는 소비 |

치수 표기는 **가로×세로×깊이**, 좌표 축은 **X=가로, Y=깊이, Z=세로**입니다. 1200×900×100의 XYZ 외곽은1200×100×900입니다. 왼쪽 창짝은 오른쪽으로, 오른쪽 창짝은 왼쪽으로 이동합니다. 요청 크기에 맞춰 레일·창짝 깊이가 함께 변합니다. 유리/프레임 간격이 부족한 조합은 변경 전에 거부합니다.

결과에는 planned, created, sections, cleanup, timing_ms, ui_update가 들어갑니다. 네 그룹(전체·본틀·좌창짝·우창짝), 세 section의 solid와 객체 경로, 손잡이 외곽, 지운 평면선/숨긴 텍스처 접합선 수를 확인할 수 있습니다. timing_ms는 plan/geometry/cleanup/native_total이며 전송·대화·최종 렌더 시간은 포함하지 않습니다.

## 고정 품질 규칙과 실행 경계

손잡이는 양 창짝 바깥 세로대의 세로 중앙에13×90mm 매립형으로 두고3mm 안으로 들어갑니다. 중앙 겹침대에서 손잡이 간섭을 피합니다. 유리는 각 창짝 안의 독립된 닫힌 볼륨이며 별도 하위 그룹은 없습니다. 기본값에서 창짝575×810×24mm, 레일 사이 창짝 간격12mm, 유리 둘레 간격0.5mm, 가스켓과 깊이 간격0.2mm입니다.

재질/뒷면재질/태그/숨김 상태가 같은 동일 평면만 정리합니다. 텍스처가 있으면 UV 영역을 보존하도록 선만 숨깁니다. 단면 모서리와 재질 경계는 유지합니다. 전체 면적과 세 section의 닫힘, 모델 외곽이 맞지 않으면 생성 전체를 취소합니다. 기존 객체 교체도 같은 Undo에 포함합니다.

기존 로컬 실행 허가·현재 세션/모델·새 명령 ID·편집 경로 검증을 사용합니다. 공유 상위 정의와 잠긴 교체 대상은 거부합니다. Ruby 임의 실행·파일 접근·편집 경로 자동 변경은 추가하지 않습니다. native 생성/정리는4초 협력적 예산이며 각 API 호출 자체를 강제 중단하지는 않습니다. 카메라와 선택을 명시적으로 바꾸지 않지만 교체로 삭제된 객체는 선택에서도 제거됩니다. 응답 유실 시 결과를 조회하고 생성을 자동 반복하지 않습니다. 이 명령은 자체 operation을 사용하므로 run_batch 단계로 중첩하지 않습니다.

## 스킬과 검증

[sketchup-sliding-window](../skills/sketchup-sliding-window/SKILL.md)는 치수 해석·재질 선택·손잡이/그룹/접합선 품질과 실행/검증 방법을 저장합니다. 기본 예제는 assets/defaults.json입니다. 예: “$sketchup-sliding-window로1500×1200×100, 왼쪽 창짝을 절반 열어 만들어줘.” 현 모델에 없는 재질 이름은 자동 생성하지 않고 조회한 재질에서 고릅니다. 스킬에는 고정 세션/모델/객체 ID를 저장하지 않습니다.

전체 자동 검사245개(Ruby202/1636 assertions, STDIO26, 외부 실행기6, 파이프 통합11), 실패/오류/생략0. [실행 로그](validation-0.7.0.txt). 기본 계획기의 모든 면/재질 역할을 실제0.6.3 최적화 창의 수치 fixture와 비교했고 일치했습니다. 다양한 치수·열림·잘못된 조합·실패 전체 취소·교체 Undo·실행 허가·중복 방지·예산·텍스처 보존을 검사했습니다.

**0.7.0 신규 명령의 설치 후 native 검사는 아직 미실행**입니다. API 대역은 환형 메시를 지운 뒤의 구멍면 표현을 완전히 지원하지 않아 창 생성 통합 fixture는 최적화를 기록만 합니다. 실제 정리 함수는 분할 큐브로 별도 검사했고, 원형 창은0.6.3에서 실제 native 최적화·외곽·세 솔리드를 확인했습니다. 이것을 신규 명령의 native 통과로 간주하지 않습니다.

다음 설치 후 확인: 새 어댑터/GUI/RBZ0.7.0과40도구 → 새 session/model/허가 → 시험 모델에서 기본창과 크기·열림 변경창 생성 → 외곽/네 그룹/세 solid/접합선/손잡이 확인 → 한 번의 Undo 및 명시적 교체 실패/복구. 기존56항목 self-test는 유지되며 새 창 명령은 별도 검사입니다. 실행 중인0.6.3과 사용자 창은 이번 개발 검사에서 변경하지 않았습니다.
