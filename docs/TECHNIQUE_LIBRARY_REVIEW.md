# SketchUp 기법 프로그램 라이브러리 검토 — 2026-10-28

상태: **도입 타당, 단계적 공통화 권고**. 기준 소스는 main의0.7.0(1911f57)입니다. 이번 검토는 소스 분석·순수 수치 측정·설계 기록이며 새 라이브러리 명령을 구현하거나 실행 중인 사용자 모델을 변경하지 않았습니다.

## 1. 판단과 역할

반복되는 스케치업 기법을 검증된 Ruby 프로그램으로 배포하면 AI가 매번 좌표·면 목록·실행 순서·정리 대상을 만드는 범위를 줄일 수 있습니다. AI는 의도를 해석하고 기법과 매개변수를 선택하며, 프로그램이 기하 계산·생성·검사를 수행합니다. 계산 자체가 없어지는 것이 아니라 결정적인 계산을 로컬 코드로 옮깁니다. 자유 형상 해석과 새로운 디자인 판단은 계속 AI/사용자 영역입니다.

| 계층 | 담당 | 예 |
| --- | --- | --- |
| AI·스킬 | 의도 해석, 라이브러리 선택, 모호한 조건 해결, 시각적 평가 | 두 짝 미닫이, 1500×1200×100, 좌창짝 절반 열기 |
| 기법 라이브러리 | 좌표·분할·간격·단면·배열 계산, 재질 역할·그룹 구조, 검증과 요약 | 레일 간격, 손잡이 위치, 단면 접합, 면 방향 |
| SketchUp 실행기 | 기존 모델/재질 해석, native API 호출, 하나의 Undo와 실패 취소 | 그룹/면 생성, 재질 적용, 선 정리, 외곽/솔리드 확인 |
| Probe GUI·MCP 어댑터 | 목록·계약 전달, 대상/권한/매개변수 확인, 결과 중개 | 현재 세션·모델·명령 ID, 지원 버전 |

**배포는 Probe와 함께, 실제 형상 실행은 SketchUp 확장(RBZ) 내부**가 적합합니다. Probe.exe에서 별도 모델 엔진을 새로 만들 필요가 없습니다. AI가 실행할 임의 Ruby를 요청마다 전송하는 방식도 필요하지 않습니다.

## 2. 이미 있는 기반과 아직 없는 것

- `geometry_plan.rb`: 순수 수치 연산, 평면/자기 교차/메시 검사, 제한된 Offset, 호·Bezier·회전체 계산.
- `sliding_window_plan.rb`: 치수로 창 단면·창짝·유리·손잡이 좌표와 면, 재질 역할을 만드는 첫 조립품 레시피.
- `sliding_window_commands.rb`: 기존 재질 해석, 형상 생성, 평면선 정리, 외곽·솔리드 확인과 한 operation. 창에 묶여 있는 빌더/정리 로직은 공통화 대상.
- `ui_update_scope.rb`: operation/Undo·실패 취소·마지막 UI 갱신의 공통 실행 경계.
- `batch_commands.rb`: 이미1–64단계를 한 메시지로 처리. 단, 앞 단계 생성 ID를 뒤 단계에서 참조하지 못하고 dry_run도 앞 단계 효과를 시뮬레이션하지 않음.
- `ToolkitCatalog.template`·생성 스크립트: C#에 포함되는 정적 형식 검사. 아직 기법별 목록·상세 조회·호환성 협상이나 공통 라이브러리 등록부는 없음.

따라서 첫 창은 이미 라이브러리화의 사례지만, 파일을 모으기만 하면 범용 기법 라이브러리가 되는 것은 아닙니다. 공통 계약·발견 방법·조합 실행·native 검증을 더해야 합니다.

## 3. 옮길 가치가 큰 후보

| 우선도 | 후보 | AI에서 줄이는 일 | 현재 상태·초기 범위 |
| --- | --- | --- | --- |
| 1 | 단면 프레임·패널·유리·매립 손잡이와 두 짝 창 | 부재 치수·꼭짓점·면·역할 재계산 | 창 구현 있음. 현재 형태를 공통 빌더로 옮기고 같은 결과 보장 |
| 1 | 내부 분석·검사·보수적 정리 | 면/선을 건별 조회해 판단·지정 | 창 전용 정리 있음. 지정 컨테이너 안에서 평면선·닫힘·외곽·그룹 깊이를 요약 |
| 2 | 선형·격자·원형 반복 배치 | 각 배치의 좌표·각도와 생성 ID 추적 | 복제/기존 정의 배치는 있음. 간격/개수 계산과 한 요청 묶음은 신규 |
| 2 | 단순 단면 돌출·문틀·몰딩·레일 | 같은 단면/모서리 조립의 반복 | push_pull·제한 sweep 기반. 허용 단면/경로부터 명시 |
| 3 | 문·선반·난간·계단 등 조립품 | 부품 분할과 간격/높이 배분 | 신규 레시피. 실제 반복 요청이 있는 품목부터 추가 |

모든 모델에 같은 정리를 적용하지 않습니다. 재질 경계·텍스처 UV·실제 단면 모서리는 유지하고, 대상이 명확한 컨테이너만 처리합니다. 곡면 감축·임의 구멍 Offset·복잡한 Boolean·어떤 모델이든 자동 재구성하는 기능은 초기 라이브러리의 보장 범위로 넣지 않습니다.

## 4. 권장 구조와 인터페이스

세 부분을 분리합니다.

1. **Planner**: 정규화한 mm 입력을 받아 순수 수치 계획과 부재 역할을 만듦. 모델 객체/영구 ID/UI에 의존하지 않음.
2. **Builder/Analyzer**: 주어진 collection/context에 만들거나 검사함. 스스로 operation을 시작하지 않음. 내부에서 얻은 부재 객체를 직접 연결하므로 AI가 생성 ID를 다시 읽을 필요가 없음.
3. **Executor**: 입력·현재 모델·재질·교체 대상을 확인하고 최상위 operation 하나를 소유. 자식 기법 호출, 결과 확인, 실패 전체 취소와 요약을 담당.

중요한 변경은 창 명령의 자체 operation과 조립 로직을 분리하는 것입니다. 현재 창 명령은 run_batch의 하위 단계가 아니며 그대로 중첩하면 안 됩니다. SketchUp operation은 중첩되지 않고 다음 시작이 앞 작업을 닫을 수 있습니다. [공식 operation 계약](https://ruby.sketchup.com/Sketchup/Model.html#start_operation-instance_method).

외부 도구는 기법마다 계속 늘리기보다 다음 **세 개의 공통 도구**를 제안합니다. 이름은 설계안이며 현재 도구가 아닙니다.

- `sketchup_list_techniques`: 현재 확장이 제공하는 기법의 ID·버전·짧은 설명·지원 상태를 읽음. 전체 스키마/메시를 한꺼번에 반환하지 않음.
- `sketchup_get_technique`: 선택한 기법의 정확한 매개변수 계약·기본값·한계·결과/품질 규칙을 읽음.
- `sketchup_run_technique`: 기법 ID·정확한 버전·params·현재 모델 실행 문맥을 받아 실행. 기존 dry_run/명령 이력/중복 방지 적용.

예를 들어 AI는 `window.sliding.two_panel@1`과 width/height/depth/opening/materials를 전달하고, 프로그램이 내부 부재를 조립합니다. 결과는 최상위 경로·부재별 역할·외곽·검증·경고·소요 시간으로 요약합니다. 상세 메시나 개별 면 목록은 필요한 진단에서만 읽습니다.

등록 정보는 기법 ID·기법 버전·최소 확장/SketchUp 버전·매개변수 스키마·역할·형상/시간 예산·검증 상태·내용 해시를 포함하는 **하나의 빌드용 원본 목록**을 둡니다. 이 목록에서 C#용 계약과 Ruby용 등록 정보를 생성하고 두 쪽의 목록 버전/해시가 맞는지 확인합니다. 초기에는 검토된 코드만 배포본에 포함합니다. 현재 C# 검사기를 그냥 우회해 자유 options를 받는 방식은 피합니다.

고급 조립에서는 라이브러리 내부의 이름 있는 부품 참조를 사용할 수 있지만, 이것은 임의 스크립트/표현식 실행 기능과 구분해야 합니다. 첫 단계는 창 한 종류로 계약을 고정하고 범용 외부 조립 DSL은 후순위로 둡니다.

## 5. 배포·성능·호환성

라이브러리 Ruby와 내부 등록 정보는 기존 RBZ 안에 넣습니다. C# 계약은 어댑터/GUI에 포함합니다. 설치 ZIP은 현재의 **EXE2개+설정2개+RBZ1개=5파일**을 유지할 수 있습니다. 배포에 Python/Node를 추가할 이유는 없습니다. 스킬은 기법 선택과 디자인 판단을 돕는 별도 자산으로 유지합니다. 자동 학습한 기법을 검사 없이 실행 코드로 등록하지 않습니다.

캐시는 첫 도입의 필수 조건이 아닙니다. 같은 도형의 순수 수치 계획은 기법 버전/해시·정규화 치수·공차·정밀도를 키로 재사용할 수 있습니다. 모델 객체/PID/재질 핸들을 컴퓨터나 문서 사이에 캐시하지 않습니다. 모델 분석 캐시는 modified 플래그만으로 무효화할 수 없으므로 초기에는 재조회합니다. 동일 부품의 component definition 재사용은 사용자 수정/공유 영향 확인을 전제로 별도 도입합니다. 최상위 그룹 수를 줄인다는 이유로 모든 부품을 무조건 해제하지 않습니다.

현재2019/2020 지원에서는 기존 native 생성 경로를 유지하는 것이 우선입니다. `fill_from_mesh`는 오래된 버전에서도 있지만, `Entities#build`/EntitiesBuilder는2022 이상입니다. 라이브러리로 AI 계산을 줄이는 일과 bulk API로 native 생성을 빠르게 하는 일은 별도 개선이며, 후자는 재질·면 매핑·닫힘·Undo의 실제 비교가 필요합니다. [공식 mesh API](https://ruby.sketchup.com/Sketchup/Entities.html#fill_from_mesh-instance_method), [Builder 버전](https://ruby.sketchup.com/Sketchup/Entities.html#build-instance_method).

SketchUp API 실행은 기존 UI 스레드 경로에 두고, 긴 작업을 별도 스레드로 옮기거나 현재4초 협력적 예산을 무작정 늘리지 않습니다. 대량 작업은 시작 전 개수/면수/응답 예산을 확인합니다. 취소 가능한 여러 요청으로 나누면 Undo도 여러 개가 될 수 있으므로 원자성과 UI 응답성의 계약을 먼저 정해야 합니다.

## 6. 확인한 계산량과 앞으로 측정할 것

SketchUp2020의 Ruby2.5.5 DLL 호스트에서 기존 `SlidingWindowPlan.build`만 측정했습니다. 각 크기5회 워밍업 후100회, monotonic 시간 기준입니다. 세 경우 모두 꼭짓점224개·면220개(정리 전). 아래 bytes는 공통 전송/원점/이름/재질을 제외한 수치·구성 매개변수와 실제 section 메시 JSON의 비교입니다.

| 가로×세로×깊이 mm | 입력 JSON bytes | section 메시 JSON bytes | 계획 중앙값 ms | p95 ms |
| --- | --- | --- | --- | --- |
| 1200×900×100 | 163 | 9562 | 6.287 | 9.942 |
| 900×1800×150 | 163 | 10368 | 5.554 | 10.875 |
| 1500×1200×100 | 164 | 9666 | 5.193 | 10.490 |

이는 프로그램에 소수의 매개변수를 주어 상세 형상을 계산시킬 수 있다는 근거입니다. **AI 토큰·벽시계 시간·파싱 비용·native 생성·렌더 개선율을 측정한 결과는 아닙니다.** 이미0.7.0 창 명령은 매개변수 방식이므로 공통 라이브러리로 옮기기만 해서 그 창이 다시 크게 빨라진다고 보장하지 않습니다. 주된 이득은 이 방식을 다른 기법과 분석 작업에도 재사용하는 것입니다.

후속 비교는 같은 요청·같은 모델·같은 품질/재질/세부도에서 일반 도구 조합과 기법 호출을 비교합니다. MCP 호출/응답 바이트·AI 토큰(측정 가능 시)·대화 포함 전체 시간·전송/plan/native/cleanup 시간·면/선/정의/그룹 수를 구분합니다. 수치 외곽/닫힘/재질 보존·시각 확인·한 Undo/실패 전체 취소도 함께 통과해야 합니다. 현재245개 자동 검사는 기존0.7.0 기록이며 이번 문서 검토에서 다시 실행하지 않았습니다.

## 7. 권장 도입 순서

1. 준비된0.7.0 창 명령을 실제 SketchUp에 설치해 생성·정리·치수/열림 변경·교체·Undo를 확인. 기존56항목 suite와 별도이며 아직 미실행.
2. 같은 창 결과를 보존하면서 plan/builder/executor를 분리하고 등록부·목록/상세/공통 실행을 추가. 기존 전용 창 도구는 같은 구현의 호환 래퍼로 유지.
3. 다른 기법에서도 바로 쓰는 **단면 프레임/패널**, **컨테이너 내부 검사·정리**, **반복 배치**부터 확장. 기법마다 지원 범위와 native 결과를 기록.
4. 실제 모델에서 시간/데이터/품질을 비교한 뒤 정의 재사용·캐시·버전별 bulk 빌더 최적화를 선택.

도입의 우선 목표는 매번 AI가 기하학 실행 절차를 재구성하는 일을 줄이고, 검증된 작업을 작은 매개변수 계약으로 재현하는 것입니다.
