# Probe 측 동적 기법 라이브러리 검토 — 2026-10-29

후속 상태: 0.8.0에서 Probe 라이브러리/내장 Jint 엔진/선택형 공유 패키지를 구현했습니다. [사용 안내와 구현 한도](PROBE_LIBRARY_RUNTIME.md), [개발 검증](VALIDATION.md). 아래 ‘구현 전’ 표시는 검토 당시 이력이며 실제 SketchUp 신규 native 실기는 아직 남았습니다.

관리 도구·파일/수정본·검증/적용·공유의 구체적인 계약은 [Probe 라이브러리 관리 규격 v1 초안](PROBE_LIBRARY_SPEC.md)에 정리했습니다. 구현 전 명세이며 이 문서의 개략 설계보다 상세 계약을 우선합니다.

상태: **설계 수정, 구현 전**. 사용자는 “새 기법과 작업 중 반복 부분을 RBZ 재설치 없이 즉시 추가/수정”하는 것을 요구했습니다. 2026-10-28 검토(906c94d)의 “기법을 RBZ 안에 배포”하는 권고는 이 요구를 충족하지 못하므로 아래 설계로 대체합니다. 현재 구현은0.7.0(1911f57)의 창 전용 Ruby 명령이며, 아래 Probe 스크립트 엔진·동적 등록·공통 계획 적용 명령은 아직 구현하지 않았습니다.

## 1. 역할과 업데이트 경계

| 위치 | 역할 | 일반 기법 변경 때 |
| --- | --- | --- |
| AI·스킬 | 의도 해석, 기법 선택/작성, 치수·배치·재질 결정 | 스킬/프리셋을 필요에 따라 수정 |
| Probe의 동적 기법 라이브러리 | 기법 목록·입력 규칙, JS 계산/조립/분석, 생성 계획·검증 기대값 | 외부 파일 저장 후 다음 실행부터 반영 |
| Probe 스크립트 작업 프로세스 | 반복/조건/수학/좌표·면 계산과 계획 출력 | 실행마다 확정한 파일 버전으로 실행 |
| RBZ 공통 실행기 | 모델 조회, 제한된 생성 계획 적용, SDK 실행·Undo·실패 취소·native 검사 | 지원 연산을 조합하는 기법은 재설치 불필요 |
| MCP 어댑터 | 고정된 목록/상세/등록·갱신/실행 요청을 Probe로 전달 | 개별 기법 추가로 재빌드하지 않음 |

**기법과 그 계산은 Probe 쪽에 둡니다.** RBZ는 창·문·계단 같은 품목별 계산을 모르고, “이 그룹에 이 점/면을 만들고 이 재질 역할을 적용하라”는 공통 계획을 수행합니다. Probe에 SketchUp SDK를 직접 붙여 모델 객체를 수정하는 구조는 제안하지 않습니다.

초기에는 RBZ에 공통 계획 실행/필요한 일괄 조회 기능을 **한 차례** 추가해야 합니다. 현 run_batch만으로는 새 부품 ID 참조나 부품별 메시를 유연하게 조립할 수 없습니다. 이후 창 분할 수·손잡이 위치·프레임 계산·새 선반 조립·반복 배열 같은 기법 수정은 외부 라이브러리만 바꿉니다. 새 SDK 기능/미지원 공통 연산이 필요한 경우에만 RBZ 기능 확장이 남습니다. “앞으로 어떤 기능에도 RBZ 변경이 전혀 없다”는 약속은 하지 않습니다.

## 2. 파일 기반 기법과 즉시 갱신

Probe가 관리하는 사용자 라이브러리 폴더에 기법별 manifest.json, technique.js, 선택적 presets/tests를 둡니다. 업데이트가 덮어쓰는 설치 폴더와 분리하고 라이브러리 폴더를 설정할 수 있게 합니다. 다른 컴퓨터에는 해당 기법 폴더와 호환 공통 실행기만 전달합니다. 기법 스크립트는 기본적으로 외부 파일이며 EXE/RBZ에 고정하지 않습니다.

등록 정보에는 ID·기법 버전·설명·매개변수 JSON 스키마·필요한 공통 연산/프로토콜 버전·예산·기대 품질을 둡니다. ID는 파일 경로나 임의 클래스명이 아닙니다. 신규 등록과 수정은 파일 감지뿐 아니라 명시적인 등록/재읽기 요청으로도 처리할 수 있게 하여 AI가 작업 중 만든 반복 기법을 바로 저장·재사용할 수 있게 합니다.

갱신 시 입력 규칙과 JS 문법/계획 출력 계약을 검사합니다. 새 실행은 확정한 소스+스키마+내용 해시를 사용하고 실행 중인 기법을 중간에 교체하지 않습니다. 변경 실패는 진단을 반환하고 실행 중인 버전에 영향을 주지 않습니다. 새 버전을 요청했는데 이전 코드를 조용히 실행하지 않습니다. 파일 감지 중복/저장 중간 상태도 이 로딩 경계에서 정리합니다.

## 3. 스크립트 엔진 선택

현재 Probe는 .NET Framework4.8/C#5이므로 **Jint 기반 JavaScript 엔진**을 첫 후보로 검토합니다. 현재 공식 문서는 core의 .NET Framework4.7.2 대상을 명시하므로4.8 호스트의 후보가 됩니다. 실제 도입 버전/종속 DLL·C#5 호출 방식·라이선스 포함·부하 측정은 구현 시 고정해야 합니다. [공식 지원 플랫폼](https://sebastienros.github.io/jint/guide/supported-platforms).

단순 계산식만 있는 JSON 규칙은 간단하지만, 창 분할·단면 조립·반복·조건이 늘면 별도 언어를 만드는 부담이 큽니다. 별도 Node/Python 설치를 요구하는 방식보다 Probe가 JS 엔진을 함께 제공하고 같은 언어로 기법을 작성하는 쪽을 우선합니다. V8 등 고성능 엔진은 실제 병목을 확인한 뒤 비교합니다.

운영 형태는 GUI 안에서 스크립트를 무제한 직접 돌리기보다 **Probe가 관리하는 별도 작업 프로세스**를 권고합니다. 이 프로세스에 JS 엔진을 포함하고 계산만 맡겨 GUI 응답과 계산 중단을 분리합니다. 별도 프로세스 자체가 파일/네트워크 권한을 격리한다는 뜻은 아닙니다. 스크립트에는 일반 CLR/임의 호스트 객체를 노출하지 않고 필요한 수학·계획 작성 API만 둡니다. 실행 시간·출력 크기·메모리·재귀/반복 예산과 부모 프로세스의 종료 처리가 필요합니다. Jint 자체도 인터프리터와 OS 격리는 별개라고 설명합니다. [Jint 공식 설명](https://github.com/sebastienros/jint).

기존 설치 ZIP5개 계약은 엔진 DLL 의존성 때문에 별도 검증 항목입니다. 엔진/작업 모드를 Probe EXE의 포함 자원·실행 모드로 제공하는 방안을 검토할 수 있지만, 아직 구현/패키징 검증 없이5파일 유지 완료로 간주하지 않습니다. 사용자 기법 파일은 설치 ZIP과 별도로 추가/공유할 수 있습니다.

## 4. 실행 흐름과 공통 계획

사용자 “1500×1200×100, 좌창짝 절반 열림”
→ AI가 기법 ID와 매개변수 전달
→ Probe가 입력 규칙 확인·현재 기법 버전 고정
→ 필요하면 RBZ에서 대상/재질/형상 정보를 일괄 조회
→ JS가 좌표·면·조립과 검사 기대값 계산
→ Probe가 계획 구조·연산/크기/예산 확인
→ RBZ가 현재 모델·문맥·허가를 다시 확인하고 한 operation에서 적용
→ 부품 역할·외곽·실제 검증 결과를 Probe/AI에 요약.

계획은 코드가 아닌 정해진 데이터 계약으로 둡니다. 초기 연산은 group/mesh/transform/existing-material/erase-explicit-target/보수적 cleanup/검증 등, 기존 창을 옮기는 데 필요한 집합으로 좁힙니다. 부품은 요청 내부의 이름으로 참조하고 RBZ가 native 객체와 연결합니다. SDK 객체/PID를 스크립트나 다른 문서에 캐시하지 않습니다. 기법 입력은 매개변수이고 상세 좌표는 Probe→RBZ 경계에서만 전송하므로 AI가 면마다 호출하지 않습니다.

이미 그린 객체의 반복 분석도 Probe가 제어할 수 있습니다. 다만 현재 get_entity_info의 개별 조회를 Probe가660회 대신 호출하기만 하면 AI 왕복은 줄어도 파이프/SDK 읽기 비용은 남습니다. RBZ는 특정 컨테이너의 정해진 범위 스냅샷/요약을 페이지 단위로 반환하는 일반 조회를 제공하고 Probe가 분류합니다. native 인접 관계·솔리드/UV 보존 판정은 공통 실행기가 최종 확인합니다. 분석 중 사용자가 모델을 바꿀 수 있으므로 실행 직전 대상과 관련 형상을 검증하고, 별도의 관찰자 기반 revision 계약 없이 modified 플래그를 신선도 보증으로 쓰지 않습니다.

외부 기법에서 복잡한 조립/검사를 계산할 수 있어야 하므로 공통 계획은 단순 box/move 매크로만으로 제한하지 않습니다. 반면 무한한 SDK 호출 문자열/Ruby eval을 실행하는 기능으로도 만들지 않습니다. 현재 허가·잠김/공유 정의·선택/편집 문맥·중복 방지·실패 복구는 공통 실행 계약으로 유지합니다.

## 5. 발견·형식 검사와 응답 유실

현재 MCP tools/list와 ToolCatalog 검사가 정적 C# 스키마를 사용합니다. 새 기법마다 C#에 필드를 추가하면 즉석 갱신 요구가 다시 막힙니다. 목록/상세/등록·갱신/실행을 고정 도구로 노출하고, 외부 매개변수는 제한된 크기의 params 객체로 전달한 뒤 Probe가 **그 기법의 동적 스키마**로 엄격히 확인하는 방식이 필요합니다. 전달용 객체에 제한을 두는 것과 기법별 스키마를 고정 EXE에 넣는 것은 구분합니다. 공통 계획 자체는 Probe와 RBZ에서 별도로 검사합니다.

공통 도구의 MCP 명칭과 정확한 계약은 구현 시 정하고, 현재 도구로 존재한다고 안내하지 않습니다. 새 기법 목록은 Probe에서 즉시 갱신되므로 MCP 도구 자체를 기법마다 추가하거나 클라이언트를 재시작할 필요가 없게 합니다. 실행 대상 RBZ의 지원 연산·프로토콜과 맞지 않는 기법은 실행 전에 거부합니다.

Probe 실행 작업 ID와 최종 native command_id를 연결해야 합니다. 계산만 실패했는지 모델 변경 요청이 제출됐는지 구분하고, 제출 시 기법/계획 해시·ID 매핑을 보관합니다. 모델 변경 제출 후 응답이 유실되면 JS 계산부터 자동 반복하지 않고 기존 command_id의 결과를 조회합니다. 기법 파일이 바뀌어도 이미 제출한 작업의 버전과 계획은 바뀌지 않습니다.

## 6. 통신·Undo와 구현 범위

현 SketchUp 파이프는65536바이트/frame, batch 입력48000바이트, 응답 약44000바이트, 응답 대기8초, native batch/창 작업4초 협력적 예산입니다. 현 기본창 수치 계획은 약10KB라 작은 첫 사례에 적합합니다. 기법별 자동 크기 예측과 계획 크기 검사는 필요합니다. 이 숫자는 새로운 공통 계획 도구의 확정 한도가 아니라 기존 코드의 제약입니다.

큰 계획을 나눠 전송하는 것과 여러 번 모델을 변경하는 것은 다릅니다. 초기에는 한 요청으로 적용 가능한 계획으로 제한합니다. 이후 필요하면 모델을 건드리지 않는 제한된 임시 계획 업로드를 여러 frame으로 받고, 마지막 apply 한 요청 안에서 operation을 열어 실행할 수 있습니다. 불완전 업로드는 생성하지 않고 세션/모델별 크기·만료/취소·검증을 둡니다. 여러 요청/타이머 틱에 걸쳐 SketchUp operation을 열어 두지 않습니다. 여러 apply로 나누면 Undo도 여러 개가 될 수 있음을 계약에 반영합니다.

기법 스크립트 계산 시간은 native 요청을 보내기 전 Probe 작업 단계로 분리합니다. native 요청의8초 대기만 늘려 스크립트 계산·업로드·실행 전체를 우겨 넣지 않습니다. 사용자에게는 계획/적용 상태를 구분해서 보여줍니다.

## 7. 다음 구현과 확인할 조건

1. 현재0.7.0 창의 실제 검증과 별도로 Probe 외부 파일 등록부·동적 스키마·JS 작업 실행을 만든다. 기존 RBZ 전용 창 명령을 공통 라이브러리의 장기 기반으로 확장하지 않는다.
2. 기존 Ruby 창 수치 계획을 JS 기법으로 옮기고 실제0.6.3 최적화 창 fixture와 좌표/면/재질 역할을 비교한다. JS/Ruby 부동소수점 차이는 기존 공차로 확인한다.
3. RBZ 공통 계획 실행기와 일괄 조회를 한 차례 추가하고 네 그룹/세 솔리드/재질/접합선·한 Undo·실패 전체 취소를 실제 SketchUp에서 검사한다.
4. **실행 중인 SketchUp/Probe/MCP를 재시작하지 않고** 기법 파일의 손잡이 위치/분할/치수를 수정하고 다음 실행에 반영되는 것을 검사한다. 진행 중 실행은 기존 버전 유지·실패한 갱신 진단·잘못된 입력 변경 전 거부도 확인한다.
5. 같은 공통 연산만 쓰는 배열/선반 기법을 신규 파일로 등록해 EXE/RBZ 변경 없이 실행되는 것을 확인한다. 다른 컴퓨터의 라이브러리 폴더 전달과 연산 버전 불일치 거부도 확인한다.
