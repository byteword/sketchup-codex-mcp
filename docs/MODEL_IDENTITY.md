# 모델 전환 식별 수정 — 0.4.1

2026-10-28, 0.4.0 실기에서 관찰한 모델 ID 유지 문제의 원인과 수정입니다. 새 도형 도구는 추가하지 않았으며 MCP 도구는 19개입니다.

## 원인

기존 `Panel#metadata`는 `@model.equal?(Sketchup.active_model)`이 거짓일 때만 문서 ID를 갱신했습니다. Windows에서 New/Open이 기존 Ruby Model 객체를 재사용하면 이 조건으로는 새 문서의 수명을 구분할 수 없습니다. 실제 시험에서도 기존 작업 모델과 새 빈 모델의 제목·경로·내용이 바뀌었는데 같은 `model_id`가 보고됐습니다.

프로세스 연결을 나타내는 `session_id`는 유지해도 되지만, 문서 대상 검사에 쓰는 `model_id`는 새로 열거나 만든 문서마다 바뀌어야 합니다. 기존 Session의 모델 불일치 검사는 ID가 실제로 바뀌어야 작동하므로, 메타데이터 UUID를 수동 교체하던 기존 통합 시험으로는 이 누락을 재현하지 못했습니다.

## 수정

- `ModelIdentity < Sketchup::AppObserver`를 등록하고 Panel이 강한 참조를 유지합니다. 등록 실패 시 제어 패널 초기화를 중단합니다.
- `onNewModel`/`onOpenModel`에서 객체·제목·경로가 같아도 새 UUID를 발급합니다. 시작 모델 알림도 받습니다.
- 실제 활성 Model 객체가 바뀌면 객체 비교를 보완 경로로 사용합니다. 같은 모델의 반복 조회·편집·저장·다른 이름으로 저장에는 ID를 임의 변경하지 않습니다.
- 알림에서 즉시 Session을 동기화하고 기존 허가·lease·소유자를 회수하며 실행 중 데모를 취소합니다. 허가 버튼을 처리하기 전에도 동기화합니다. 기존의 요청 실행 전 검사도 유지합니다.
- 이전 모델 ID의 조회·변경 요청은 실행기 진입 전에 `model_mismatch`로 거부합니다. 새 모델 ID만 알고 있어도 새 허가 없이는 변경할 수 없고, 새 허가 이후에도 이전 lease는 유효하지 않습니다.
- `session_id`, 명령 연속번호와 과거 결과 이력은 유지합니다. 과거 결과 조회는 원래 모델 ID로 가능하지만, 이를 새 모델에서 재실행하는 것은 허용하지 않습니다.

파일 경로는 Save As로 바뀌고 미저장 모델은 모두 빈 문자열일 수 있습니다. `Model#guid`도 편집·저장 후 바뀌므로 문서 수명 키로 사용하지 않았습니다. 근거: [공식 AppObserver 알림](https://ruby.sketchup.com/Sketchup/AppObserver.html), [Model#guid](https://ruby.sketchup.com/Sketchup/Model.html#guid-instance_method), [Sketchup.add_observer](https://ruby.sketchup.com/Sketchup.html#add_observer-class_method).

## 자동 검증

전체 **137개 통과**, 실패·오류·건너뜀 0입니다. Ruby 112개 / 684 assertions, Python STDIO 19개, 실제 MCP → 제어 허브 → Win32 파이프 → Ruby 통합 6개입니다. Ruby 문법 검사와 .NET Framework x64 빌드도 통과했습니다. [실행 로그](validation-0.4.1.txt)를 보관합니다.

새 회귀 12개는 같은 Ruby 객체와 동일 제목/경로에서의 New/Open ID 갱신, Save/Save As 안정성, 타이머 전 이전 요청 차단, 새 허가·lease 필요, 이력/번호 유지, 데모 취소, 활성 객체 변경 보완을 검사합니다. 실제 파이프 통합 시험도 프로덕션 `ModelIdentity`의 알림을 호출하도록 바꿨고, 새 회귀는 같은 wrapper·같은 대상 PID를 유지한 채 New/Open 후 오래된 요청 거부와 다른 인스턴스의 분리를 확인합니다.

이 자동 시험의 앱 알림과 모델은 대역입니다. 설치된 Ruby 2.5.5 DLL을 실행했다고 실제 SketchUp의 알림 발생 자체를 검증한 것은 아닙니다. 수정 개발 당시에는 실행 중인 0.4.0 앱/모델을 종료하거나 새 확장을 자동 설치하지 않았습니다.

## 실제 앱 확인 — 2026-10-28

이후 사용자가 0.4.1로 교체했습니다. 같은 프로세스·세션에서 New와 동일 파일 다시 열기 모두 새 모델 ID 발급 및 기존 허가 자동 회수를 확인했습니다. 이전 ID의 조회/변경 미리보기는 거부, 새 ID 조회는 성공, 사용자 제어에서 변경 미리보기는 차단됐습니다. 미저장 모델의 최초 파일 저장에는 ID가 유지됐습니다. 형상을 수정하지 않았으며 종료 상태는 사용자 제어·`modified=false`입니다.

실제 형상 변경·이전 lease·편집 후 저장/Save As·경합 등 미확인 조건과 확인 근거는 [0.4.1 실기 결과](MANUAL_RESULTS_0.4.1.md)에 구분했습니다.

## 설치 후 실제 확인 순서

1. 작업을 저장하고 GUI·MCP·SketchUp을 종료합니다. [시험 배포 안내](TEST_RELEASE.md)에 따라 EXE/설정 4개와 `su_pipe_probe-0.4.1.rbz`를 함께 교체하고 다시 실행합니다.
2. 연결 목록/상태의 확장·중개 앱 버전 `0.4.1`, 현재 `session_id`와 `model_id`를 기록합니다. 시험 모델에서 실행 허가를 줍니다.
3. SketchUp에서 **파일 → 새로 만들기**를 실행합니다. 세션은 유지하고 모델 ID가 달라지며 권한이 사용자 제어로 바뀌는지 확인합니다.
4. 이전 모델 ID의 정보 조회가 `model_mismatch`로 거부되는지 확인합니다. 새 모델 조회는 허가 없이 성공하고, 새 변경은 새 허가 전까지 차단되어야 합니다. 실제 변경 시험은 새 시험 모델에서 새로 확인한 ID만 사용합니다.
5. **파일 → 열기**, 같은 파일 다시 열기, 연속 새 모델 만들기에서도 확인합니다. 로컬 저장·다른 이름으로 저장만 할 때는 모델 ID와 허가가 유지되는지도 대조합니다.

위 절차에서 확인한 부분은 [0.4.1 실기 결과](MANUAL_RESULTS_0.4.1.md)에 추가했고, 기존 [0.4.0 실기 기록](MANUAL_RESULTS_0.4.0.md)은 당시 이력으로 유지합니다. 이후 기능 순서는 [드로잉·정보조회 계획](FEATURE_PLAN.md)에 있습니다.
